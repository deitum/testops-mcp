# Формат Markdown для импорта тест-кейсов

Этот документ задаёт формат файлов для `testcase_import_markdown`. MCP перед загрузкой проверяет структуру и преобразует имена custom fields и значений во внутренние ID TestOps.

## 1. Требования к файлу

- расширение: `.md` или `.markdown`, регистр расширения не важен;
- кодировка: UTF-8, BOM допускается;
- максимальный размер: 2 MiB;
- в MCP передаётся абсолютный путь к файлу;
- файл должен находиться внутри одного из каталогов из поля `allowedImportRoots`, возвращённого вместе с этими правилами;
- один файл может содержать один или несколько тест-кейсов.

## 2. Структура тест-кейса

Каждый тест-кейс начинается с заголовка второго уровня:

```markdown
## TC-01. Успешное открытие формы
```

Имена кейсов в одном файле должны быть уникальны. Сравнение выполняется без учёта регистра, лишних пробелов и различий в Unicode-представлении.

После заголовка используются секции третьего уровня:

| Русское имя | Английское имя | Обязательность | Содержимое |
|---|---|---|---|
| `Описание` | `Description` | нет | Обычный Markdown-текст |
| `Предусловия` | `Preconditions` | нет | Список предусловий |
| `Шаги` или `Сценарий` | `Steps` или `Scenario` | да | `[step]` и `[expected]` |
| `Теги` | `Tags` | нет | Список или CSV |
| `Ссылки` | `Issues`, `Links` или `Jira` | нет | Jira-style ключи |
| `Поля` или `Кастомные поля` | `Fields` или `Custom Fields` | зависит от проекта | Custom fields по именам |

Правила секций:

- одну секцию нельзя объявлять дважды в одном кейсе;
- неизвестные секции считаются ошибкой;
- `Папки` / `Folders` пока не поддерживаются и считаются ошибкой;
- обязательна секция `Шаги` / `Steps` / `Scenario`;
- остальные секции могут отсутствовать, но все required custom fields проекта должны быть явно указаны.

## 3. Описание и предусловия

Описание сохраняет абзацы:

```markdown
### Описание
Первый абзац.

Второй абзац.
```

Предусловия рекомендуется оформлять списком:

```markdown
### Предусловия
- Открыта клиентская сессия.
- У оператора есть нужные права.
```

## 4. Шаги и ожидаемые результаты

Рекомендуется помещать сценарий в fenced code block. Если fence используется, весь сценарий должен находиться внутри него.

````markdown
### Шаги
```text
[step 1] Открыть форму
    [expected 1.1] Форма открыта
    [expected 1.2] Ошибки не отображаются

[step 2] Заполнить форму
    [step 2.1] Указать клиента
        [expected 2.1.1] Клиент выбран
    [step 2.2] Нажать Сохранить
        [expected 2.2.1] Данные сохранены
```
````

Правила сценария:

- поддерживаются только маркеры `[step]` и `[expected]`;
- текст после маркера обязателен;
- суффиксы `1`, `1.1` и подобные нужны только для читаемости — связь определяется отступом;
- expected result должен быть ровно на один уровень глубже своего parent step;
- вложенный step также должен иметь parent step на предыдущем уровне;
- во всём сценарии используйте один стиль: либо табы, либо группы ровно по четыре пробела;
- attachment/shared/expected.step и другие специальные маркеры сейчас не поддерживаются;
- expected results передаются в TestOps как результаты шагов, а не как самостоятельные шаги.

## 5. Теги и ссылки на задачи

Теги можно записывать отдельными строками или через запятую:

```markdown
### Теги
- checkout
- smoke, regress
```

Повторяющиеся теги удаляются с предупреждением.

Ссылки должны содержать Jira-style ключ:

```markdown
### Ссылки
- SHOP-1234
- Связано с SHOP-5678
```

Каждый ключ загружается как внешняя ссылка на соответствующую задачу Jira: адрес строится от корня Jira из настройки сервера `TESTOPS_JIRA_BASE_URL`. Если она не задана, файл со ссылками отклоняется на этапе проверки и ни один кейс не создаётся. Импорт не создаёт и не связывает интегрированные TestOps Issues.

## 6. Custom fields

ID полей и значений в Markdown не указываются:

```markdown
### Поля
- Team: T22
- Component: UI Selenide
- Тип тестирования: Smoke, Regress
```

Переданный пример — готовый тест-кейс, демонстрирующий поддерживаемый формат. Его custom fields относятся только к этому кейсу, а не представляют каталог текущего проекта: не копируйте их в другие кейсы без исходных данных и не придумывайте отсутствующие поля или значения.

Формат строки:

```text
- Имя поля: Значение 1, Значение 2
```

Если запятая или двоеточие являются частью имени, используйте двойные кавычки. Двойная кавычка внутри quoted value экранируется второй кавычкой:

```markdown
- Component: "UI, Desktop", API
- "Field: Name": "A ""quoted"" value"
```

Как выполняется резолвинг:

1. MCP получает поля проекта через API TestOps.
2. Сначала ищется точное совпадение после Unicode-нормализации и схлопывания пробелов.
3. Затем допускается единственное совпадение без учёта регистра.
4. Нечёткий поиск и автоматическое исправление текста не выполняются.
5. Неизвестное или неоднозначное поле/значение блокирует весь upload.
6. Для single-select поля можно указать только одно значение.
7. Required поле должно быть явно записано в каждом кейсе, даже если в проекте настроен default.

## 7. Загрузка

Для обычной загрузки нужен один вызов `testcase_import_markdown` с абсолютным путём к файлу. Например:

```jsonc
{
  "filePath": "<ABSOLUTE_PATH_TO_FILE>/test-cases.md"
}
```

Проект не передаётся в MCP-команде: сервер всегда использует `TESTOPS_PROJECT_ID` из конфигурации OpenCode. Чтобы выбрать другой проект, нужно изменить конфигурацию и перезапустить сервер.

Сначала MCP выполняет preflight:

1. разбирает и проверяет весь Markdown;
2. загружает custom fields проекта из `TESTOPS_PROJECT_ID`;
3. резолвит имена полей и значений и проверяет required-поля;
4. при любой ошибке отказывается от загрузки до создания первого кейса.

После успешного preflight кейсы создаются последовательно. Этот этап не транзакционный: при ошибке предыдущие кейсы могут уже быть созданы, текущий кейс может остаться частично заполненным, а следующие не будут начаты. Автоматического rollback нет.

| Статус | Что произошло | Что делать дальше |
|---|---|---|
| `completed` | Все кейсы и их данные созданы | Использовать возвращённые ID |
| `refused` | Preflight нашёл ошибки; кейсы не создавались | Показать ошибки и ждать решения пользователя |
| `failed` | Запись остановилась на известной ошибке; предыдущие кейсы могли быть созданы полностью, а текущий — частично | Проверить `created`, `partiallyCreated`, `failedCase` и `notAttempted`, затем сверить отчёт с TestOps. Не выполнять повторный импорт, удаление кейсов или rollback автоматически |
| `outcome_unknown` | TestOps мог создать текущий кейс, но MCP не получил надёжного подтверждения | Проверить `created`, `failedCase` и `notAttempted`, затем выяснить по имени, существует ли кейс в TestOps. Не выполнять повторный импорт, удаление кейсов или rollback автоматически |

`testcase_custom_fields` не вызывается перед первой попыткой импорта. Он нужен только по явной просьбе показать каталог либо после ошибки, связанной с custom fields, когда пользователь попросил исправить файл.

## 8. Частые ошибки

| Код | Причина |
|---|---|
| `FILE_PATH_NOT_ABSOLUTE` | Передан относительный путь к файлу |
| `FILE_OUTSIDE_ALLOWED_ROOT` | Файл находится вне каталогов из `allowedImportRoots` |
| `INVALID_HEADING_LEVELS` | Тест-кейсы и их секции оформлены заголовками неверного уровня |
| `MISSING_SCENARIO_SECTION` | Нет секции шагов |
| `INVALID_SCENARIO_INDENTATION` | Использован неверный отступ |
| `ORPHAN_EXPECTED_RESULT` | Expected result не вложен в step |
| `FIELD_NOT_FOUND` | Поле не найдено в проекте |
| `FIELD_AMBIGUOUS` | Имени соответствуют несколько полей |
| `VALUE_NOT_FOUND` | Значение не найдено |
| `VALUE_AMBIGUOUS` | Значение неоднозначно |
| `REQUIRED_FIELD_MISSING` | Не указано обязательное поле |
| `MULTIPLE_VALUES_NOT_ALLOWED` | Для single-select указано несколько значений |
